# 架构说明：从 WebSocket 实时面试到预制题库 + 可重试接口

本文记录 V2 重构的原因、设计和验证结果，供后续维护参考。

## 1. 旧架构为什么在高并发下大量断连

V1 中每个学生在面试期间与后端保持 **3 条 WebSocket**（控制指令、语音上行、语音播报），后端再为每个学生建立 **1 条到百炼实时语音模型的 WebSocket**。题目和追问在面试过程中实时调用大模型生成。逐项排查后，导致高并发断连的原因如下：

| # | 问题 | 后果 |
|---|------|------|
| 1 | 同一个 `WebSocketSession` 被多个线程同时写（WebSocket 处理线程、线程池里的出题 / 追问任务、实时语音回调），且未使用 `ConcurrentWebSocketSessionDecorator` | Tomcat 抛出 `IllegalStateException: TEXT_PARTIAL_WRITING`，连接直接被关闭——**高并发断连的最直接原因** |
| 2 | WebSocket 消息处理线程里同步执行 TTS 流式播报、OSS 上传、数据库写入 | 处理线程被阻塞数秒，心跳得不到处理，前端判定超时后重连；用户一多线程被占满 |
| 3 | 每个学生 4 条长连接，其中 1 条连到百炼 | 百炼实时接口有并发上限，超出后上游断开，进而级联关闭学生的连接 |
| 4 | 录音缓冲（`VOICE_MAP`）、题目 / 追问缓存放在 JVM 静态 Map 中 | 无法多实例部署；重启即丢失进度；录音按时长预分配内存，内存压力大 |
| 5 | 线程池使用默认 AbortPolicy + 1000 队列；评分补偿任务用无上限的虚拟线程一次性全部打出去 | 高峰期任务被拒绝或形成重试风暴，触发百炼 429 限流 |
| 6 | 调用百炼的 OkHttp 使用 HTTP/2，连接超时 10 分钟 | 所有并发请求复用一条 TCP 连接，大体积音频请求互相阻塞；失败的请求要挂很久才返回 |
| 7 | Tomcat 2000 线程 vs 数据库连接池 10 | 线程大量阻塞在获取数据库连接上 |
| 8 | 面试流程依赖大模型实时出题和追问 | 任何一次模型调用慢或失败，都会直接卡住正在面试的学生 |

## 2. 新架构

核心思路：**学生答题链路上不再有长连接，也不再有同步的大模型调用。**

- **预制题库**：教师创建考核时维护题库（可用 AI 生成草稿后审核）。学生开始面试时服务端按维度均衡随机抽题，写入 `student_assessment_question_answer`（含题目、参考答案、追问的快照），抽题结果不再变化。
- **题目语音预合成**：保存题库后由后台任务调用 qwen3-tts-flash 生成并存储；学生端直接下载。没有预生成时现场合成（同一题并发只合成一次），再失败前端用浏览器朗读兜底。
- **本地录音 + HTTP 上传**：浏览器用 AudioWorklet 本地录成 16kHz WAV，每题录完一次性上传。上传失败时录音仍保留在浏览器，可原样重试。
- **服务端状态机**：面试进度完全由数据库推导（`InterviewService.buildState`），状态为 `NOT_STARTED → DEFENSE → QUESTIONS → READY_TO_SUBMIT → SUBMITTED`。所有写接口都是**幂等**的，依靠条件更新（`... WHERE answer_voice IS NULL`）和唯一索引保证：重复提交、并发点击、多标签页都会收敛到同一个状态。刷新页面后调用 `/front/interview/state` 即可恢复。
- **持久化任务队列**（`async_task` 表 + `TaskWorker`）：语音转写、评分、语音合成都作为任务入库。
  - 多实例安全：通过条件 UPDATE 抢占任务，同一任务只会被一个实例执行。
  - 崩溃恢复：执行中的任务带租约，实例宕机后租约过期，任务由其他实例接手。
  - 削峰：每类任务有并发上限，只领取空闲线程能处理的数量；高峰期任务排在库里，而不是堆在内存里。
  - 失败退避重试（15s、30s、60s…），达到上限后写入兜底结果（如"语音转写失败"），不会让评分永远等待；评分失败后教师可手动重新评分。
  - 评分任务会等全部转写完成：依赖未就绪时延后执行，不计入重试次数。
- **大模型调用治理**：`AiRateLimiter` 按能力（LLM / ASR / TTS）限制单实例在途请求数；对网络错误、429、5xx 做指数退避重试；HTTP 客户端只用 HTTP/1.1，超时按场景设置。
- **文件存储抽象**：`FileStorage` 支持 OSS 和本地磁盘（签名直链），开发、测试、私有化部署可以不依赖 OSS。
- **数据库**：`student_assessment_record (student_id, assessment_id)` 和 `student_assessment_question_answer (student_id, assessment_id, sort_index)` 加唯一索引；按主键删除，避免二级索引上的间隙锁死锁；死锁时事务自动重试。

## 3. 验证结果

单元测试 33 个全部通过（抽题、面试状态机、WAV 解析切分、题库校验、AI 输出解析等）。端到端脚本覆盖：创建 / 修改题库、语音预生成、AI 生成题库草稿、抽题、答辩、答题、追问、重复提交幂等、越序作答拒绝、提交、真实语音转写与评分、签名直链、重考重新抽题。

并发压测：每个虚拟学生完整走一遍面试流程（登录、开始、答辩上传 10s 录音、3 道题 + 追问各自下载题目语音并上传 6s 录音、提交），所有学生同时开始。

| 环境 | 并发学生 | 成功 | 错误 | 主要接口 p99 |
|------|---------|------|------|-------------|
| 开发机（32 核，Windows，Docker MySQL） | 500 | 500 | 0 | < 1.6s |
| 开发机 | 1000 | 1000 | 0 | < 2.9s |
| 测试服务器（4 核，与其他服务及压测程序共用） | 500 | 500 | 0 | 5～14s（CPU 打满时请求排队而不是失败） |

这里的压测是"所有学生在同一分钟内完成整场面试"的极端情况；真实考试中学生分散进入，每人每题只有几次请求。

后台 AI 处理能力取决于百炼账号配额：默认配置下单实例同时进行约 9 路转写、4 路评分。在开发机实测，20 名学生（108 次转写 + 20 次评分）约 3.5 分钟全部完成，期间没有失败任务。需要更快出分时，可以调高 `DASHSCOPE_CONCURRENCY_*` / `TASK_CONCURRENCY_*`（需账号配额支持），或增加实例。

## 4. 已知限制与后续工作

- 浏览器只允许在 HTTPS 或 localhost 下使用麦克风，生产环境必须配置 HTTPS。
- 重考时旧的录音文件不会自动从存储中删除，长期运行需要定期清理没有被引用的文件。
- 教师端暂不支持从 Excel 批量导入题库（目前支持逐题编辑、每行一题的批量粘贴和 AI 生成草稿）。
- 若部署多个后端实例，文件存储必须使用 OSS 或共享目录。
